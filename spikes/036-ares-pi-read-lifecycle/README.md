# Spike 036: exact ares PI DMA-read lifecycle

This isolated experiment closes one explicit gap left by the validated PI DMA-write request/queue/dispatch fixture: execute the symmetric `PI_DMA_Read` request through the real pinned ares PI, RDRAM, EventQueue and CPU synchronization paths.

## Scope

Exact reference revision: ares `9408cb43d4948fc3ea6e152a307a34348df3fe04`.

The fixture checks six cases:

1. a normal read-length MMIO request, with exact successful RDRAM halfword reads before later queue dispatch/completion;
2. PI status cancellation after the immediate copy;
3. a physically full 512-row queue, where insertion fails but the synchronous RDRAM reads still occur;
4. two equal-deadline `PI_DMA_Read` rows that must remain token-distinct and request-unbound;
5. save-only serialization, which must preserve the live external queue identity under current ADR-0057 policy;
6. save/reset/load, which must cut external identity and leave the real restored completion unknown.

The observed build uses the existing layout-neutral queue sensor plus the existing successful identity-RDRAM scalar callback generated by the headless ares builder. It does not add guest accesses or clocks. The baseline build is uninstrumented. Observer-disabled and observer-enabled reference states/facts must match, and repeated enabled output must be byte-identical.

This does **not** claim hardware timing. In the pinned ares implementation `PI::ioWrite(PI_READ_LENGTH)` attempts queue insertion and then calls `dmaRead()` synchronously; the later queue callback only drives `dmaFinished()` status/IRQ effects.
