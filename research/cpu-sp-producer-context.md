# CPU SP producer instruction/source context

Date: 2026-10-09

Status: **IN PROGRESS** pending exact-pin execution receipt.

Worker: `gpt56sol-cpu-sp-producer-context-20261009`

## Question

The bounded boot producer inventory currently associates normalized CPU SP Word
effects with the most recent same-PC fetched instruction. Can the three observed
producer families (`SW`, `SB`, `SWC1`) instead be tied to the exact decoded CPU
execution context and normalized source operand at the concrete SP sink, so PC or
payload equality is never used as causal provenance?

## Hypothesis

In pinned ares interpreter scope, the concrete CPU-originated SP Word sink occurs
synchronously inside the `CPU::instruction()` call that executes the store. A
scope around that call can therefore carry one exact instruction word/PC plus a
pre-store register snapshot into the existing SP backing observer. The verifier
should be able to re-decode the instruction and independently reproduce the sink
payload for `SW`, widened `SB`, and FR-sensitive `SWC1`.

A same-address/same-value direct CPU write outside decoded execution must remain
unattributed, and CU1-disabled `SWC1` must emit no sink.

## Exact sources inspected before implementation

Pinned ares: `9408cb43d4948fc3ea6e152a307a34348df3fe04`.

- `ares/n64/cpu/cpu.cpp`: interpreter path performs successful fetch,
  `pipeline.begin()`, `instructionPrologue(ipu.pc, instruction)`,
  `decoderEXECUTE(instruction)`, `instructionEpilogue<0>()`, then
  `pipeline.end()` in one synchronous `CPU::instruction()` call.
- `ares/n64/cpu/interpreter-ipu.cpp`: `SW` passes `rt.u32` to `write<Word>`;
  `SB` passes the full `rt.u32` to `write<Byte>`.
- `ares/n64/cpu/interpreter-fpu.cpp`: `SWC1` checks CU1 then stores `FT(u32)`.
- `ares/n64/memory/io.hpp`: the RCP subword adapter shifts the unmasked incoming
  value before the common Word sink, preserving the already validated SPMEM
  widening behavior.
- `ares/n64/rsp/io.cpp`: SP-memory Word writes select DMEM/IMEM and replace the
  concrete Word backing.

Existing Plaid evidence used read-only:

- `research/sp-producer-sites.md`: the verified bounded prefix contains 51,991
  SW, 2,256 SB and six SWC1 normalized CPU SP effects, but explicitly does not
  claim retirement or source dataflow.
- `research/cpu-rsp-imem-subword.md`: CPU SB/SH SPMEM effects normalize at the
  full Word sink and may contain source bytes above the nominal ISA width.
- `research/ares-cop1-store-mutation.md`: `SWC1` source selection depends on FR
  mode; in FR=0 an odd register selects the high 32-bit half of the paired even
  FPR, while FR=1 selects the named FPR.

## Durable experiment

`spikes/043-ares-cpu-sp-producer-context/` executes real encoded instructions
through `CPU::instruction()` with recompilers disabled and reuses the existing
project-owned `PlaidSpWordObserver` generated by the headless ares build helper.
No reference object fields or runtime semantics are changed.

The controlled sequence includes:

1. identical `SW` at one PC/address/value;
2. the identical `SW` again, requiring a new writer generation;
3. an equal-address/equal-value direct `cpu.write<Word>` with no decoded scope;
4. `SB +1`, requiring the widened Word sink;
5. FR=0 even `SWC1`;
6. FR=0 odd `SWC1`;
7. FR=1 odd `SWC1`;
8. CU1-disabled `SWC1`, which must fault without a sink.

Observer-disabled and repeated enabled runs must preserve identical architectural
facts and outcomes. Enabled traces must repeat byte-for-byte.

## Intended interpretation

If validated, this closes only the register-level *immediate producer context*
for the tested interpreter stores. It does **not** identify where the GPR/FPR
bytes originally came from. Ultimate source provenance still needs prior
instruction/load/copy history, and the active RSP-DMEM-to-CPU-refetch worker owns
that separate composition question. Recompiler execution, arbitrary exception
interleavings, DMA, reset/restore, general store-family coverage and executable
lifetimes remain outside this slice.
